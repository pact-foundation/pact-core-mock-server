# Releasing

Each crate releases independently through its own pull request.

| Crate | Release branch | Tag | Release title |
| --- | --- | --- | --- |
| `pact_mock_server` | `release/pact_mock_server` | `libpact_mock_server-v<version>` | Pact Mock Server Library v`<version>` |
| `pact_mock_server_cli` | `release/pact_mock_server_cli` | `pact_mock_server_cli-v<version>` | Pact Mock Server Standalone v`<version>` |

`pact_mock_server_cli` builds the `pact-mock-server` binary. The tag-to-crate mapping lives in `.github/scripts/release-tags.sh`.

## Prerequisites

The release workflows need this setup outside the repository.

1. The Pact Foundation bot GitHub App is installed on the repository. The workflows read `vars.PACT_FOUNDATION_BOT_APP_ID` and `secrets.PACT_FOUNDATION_BOT_PRIVATE_KEY`. Tags pushed with the App's token start the release workflows.
2. A `crates-io` environment exists in the repository settings.
3. A crates.io trusted publisher is configured for each crate. crates.io matches the workflow that started the run, not the reusable `publish-crate.yml` it calls. Register these, with the `crates-io` environment:
   - `pact_mock_server`: workflow `release-crate.yml`.
   - `pact_mock_server_cli`: workflow `release.yml`.
   Both use repository `pact-foundation/pact-core-mock-server`.
4. The secrets `DOCKER_HUB_USERNAME` and `DOCKER_HUB_TOKEN` exist. The token has push access to `pactfoundation/pact-mock-server`.
5. The `ghcr.io/pact-foundation/pact-mock-server` package grants this repository write access.
6. Branch protection for `main` requires the `Release gate complete` and `Release dependencies` checks. Both report on every pull request, so a required check never stays pending.

## Release pull requests

On every push to `main`, the Release PR workflow keeps one draft pull request per crate with unreleased changes, on branch `release/<crate>`. Each one bumps the crate's version and adds a changelog section generated from the conventional commits since its last release.

To release a crate:

1. Review the draft `release/<crate>` pull request. Edit the version or changelog on its branch if needed. Once anyone pushes to it, the bot stops regenerating it; close it to get a fresh one.
2. Mark it ready for review. The full test suite runs.
   - For `pact_mock_server_cli`, the release gate runs too. It builds the release archives for all eight targets and checks the C library each Linux archive links against. The `Release gate complete` check reports the result.
   - For both crates, the `Release dependencies` check packages the crate against the released versions of its workspace dependencies.
3. Merge it.

A release pull request cannot merge while it requires a workspace crate version that is not yet released. Release that crate first.

## After merge

1. The Release PR workflow tags the merge commit `<prefix>-v<version>`, using the tags in the table above.
2. The tag starts a release workflow.
   - A `libpact_mock_server-v*` tag starts Release crate. It publishes the crate to crates.io through trusted publishing, then creates the GitHub release with the changelog section.
   - A `pact_mock_server_cli-v*` tag starts the dist Release workflow. It builds the archives for all eight targets, checks their linkage, and publishes the crate to crates.io. It then creates the GitHub release with the archives and the changelog section, and retitles the release.
3. After a `pact_mock_server_cli` release, the legacy asset names are uploaded to its release, and the `pactfoundation/pact-mock-server` image is pushed to Docker Hub and GHCR for `linux/amd64` and `linux/arm64`, tagged `<version>` and `latest`.

## Legacy asset names

Each `pact_mock_server_cli` release also carries the pre-dist asset names: `pact-mock-server-{linux,macos}-{x86_64,aarch64}.gz` and `pact-mock-server-windows-{x86_64,aarch64}.exe.gz`, each with a `.sha256` file. The Linux names are the musl builds.

These names are published until the legacy cut-off date, 2027-06-30, set in `.github/scripts/legacy-artifacts.sh`. After that date, delete the legacy sections of this file, along with the other files that script lists.

## Regenerating the release workflow

`.github/workflows/release.yml` is generated by dist and carries hand edits, each marked with a `# hand edit:` comment. `dist-workspace.toml` sets `allow-dirty = ["ci"]`, so `dist generate` skips the file. To regenerate it, for example after changing `dist-workspace.toml` or upgrading dist:

1. Remove the `allow-dirty = ["ci"]` line from `dist-workspace.toml`.
2. Run `dist generate`.
3. Restore the `allow-dirty = ["ci"]` line.
4. Re-apply each `# hand edit:` block from the previous version of `release.yml` (`git diff` shows them).
5. Run `dist generate --check`. It passes while the line is in place.

## Recovering a release

Each step of a release can also be run by hand. Run these commands from the repository root, with tags fetched (`git fetch --tags origin`) and the tools from `mise.toml` installed (`mise install`). Each step names the credentials it needs.

### Re-run failed jobs

Most failures are transient, or are fixed outside the repository, e.g. a missing trusted publisher. Re-run only the failed jobs of the tag's release workflow:

```sh
gh run rerun <run id> --failed
```

This covers the jobs of Release PR (`tag`, `prepare`), Release crate (`publish`, `release`), the dist Release workflow (`plan`, the builds, `custom-check-artifacts`, `host`, `custom-publish-crate`, `announce`) and the post-announce jobs. For `prepare`, the next push to `main` also reruns it.

Publishing skips a version already on crates.io. Don't re-run the whole workflow: release creation fails once the GitHub release exists.

If `host` failed, nothing has been published. Re-run it.

If `announce` created the GitHub release but failed while uploading to it, re-running it fails on the existing release. Upload the run's archives by hand instead, then run the legacy and container steps below. This needs write access to releases.

```sh
gh run download <run id> -p 'artifacts-*' -D artifacts
find artifacts -type f ! -name '*-dist-manifest.json' -exec gh release upload pact_mock_server_cli-v<version> --clobber {} +
```

If the release title is wrong because the `release-title` job failed, re-run that job, or set it by hand:

```sh
gh release edit <tag> --title "$(.github/scripts/release-title.sh <tag>)"
```

### Release again after a failed release

A tag whose release can never succeed, e.g. one that needs a code fix, blocks its crate. While the tagged version is missing from crates.io, the Release PR workflow skips that crate. Deleting the tag doesn't help: the next push to `main` would tag the same version again.

Release the next version instead, from a release pull request opened by hand. It needs push access to the repository.

```sh
git switch -c release/<crate> origin/main
release-plz set-version <crate>@<next version> --config release-plz.toml
git commit -am "chore(<crate>): release v<next version>"
git push --force origin release/<crate>
gh pr create --draft --base main --head release/<crate> \
  --title "chore(<crate>): release v<next version>" \
  --body-file <(.github/scripts/changelog-section.sh <crate>/CHANGELOG.md <next version>)
```

`set-version` runs from the repository root, where the changelog paths in `release-plz.toml` resolve. It bumps the version in the crate's `Cargo.toml` and in `Cargo.lock`, and retitles the newest changelog section, which is the failed release's section. Add the fix's changelog entry to that section by hand. The bot never regenerates a release pull request that has commits from people. The failed version's tag stays, and no release ever ships under it.

### Open a release pull request without the bot

If the Release PR workflow can't run at all, e.g. while the bot App is unavailable, open the pull request the same way as above, with `release-plz update -p <crate> --manifest-path Cargo.toml --config release-plz.toml` in place of `set-version`. It computes the version and the changelog from the commits since the last release.

### Tag a merged release

The Release PR workflow tags each version with no tag. If its `tag` job fails, re-run it, or tag by hand. This needs push access to tags.

```sh
.github/scripts/tag-releases.sh Cargo.toml origin
```

The script tags the commit that set each untagged version, and refuses a version that is already on crates.io. A tag pushed with your own credentials starts the release workflow, as the bot's does.

### Publish to crates.io

Trusted publishing works only from the release workflows. To publish by hand, you need an owner's crates.io API token with the `publish-update` scope.

```sh
git switch --detach <tag>
cargo login
cargo publish -p <crate> --locked
```

Then re-run the failed jobs of the tag's release workflow. Its publish job skips the version, and the GitHub release follows.

### Create the library's GitHub release

The `pact_mock_server` GitHub release carries only the changelog section. If the `release` job of Release crate failed, re-run it, or create the release by hand. This needs write access to releases.

```sh
.github/scripts/changelog-section.sh pact_mock_server/CHANGELOG.md <version> > notes.md
gh release create libpact_mock_server-v<version> --verify-tag \
  --title "$(.github/scripts/release-title.sh libpact_mock_server-v<version>)" --notes-file notes.md
```

The `pact_mock_server_cli` release carries the archives built by the dist workflow, and only that workflow builds every target. Re-run its failed jobs.

### Publish legacy asset names

If the legacy job failed, re-run it. When the fix is a change to the legacy script, run the Legacy artifacts workflow with the release tag instead. It runs the script from `main`, while a re-run uses the tagged commit's.

```sh
gh workflow run legacy-artifacts.yml -f tag=pact_mock_server_cli-v<version>
```

To build and upload them locally instead, you need write access to releases:

```sh
GITHUB_REPOSITORY=pact-foundation/pact-core-mock-server \
  .github/scripts/legacy-artifacts.sh pact_mock_server_cli-v<version> out
gh release upload pact_mock_server_cli-v<version> --clobber out/*
```

### Publish the container image

Run the Publish containers workflow with the version:

```sh
gh workflow run publish-containers.yml -f version=<version>
```

To push locally instead, log in to Docker Hub with push access to `pactfoundation/pact-mock-server`, and to GHCR with a token that has the `write:packages` scope. The image downloads the musl archives from the `pact_mock_server_cli-v<version>` release, so that release must exist. Building both platforms needs a buildx builder that supports them, e.g. one made with `docker buildx create --use`.

```sh
docker login
docker login ghcr.io
docker buildx build pact_mock_server_cli \
  --platform linux/amd64,linux/arm64 \
  --build-arg VERSION=<version> \
  --tag pactfoundation/pact-mock-server:<version> \
  --tag pactfoundation/pact-mock-server:latest \
  --tag ghcr.io/pact-foundation/pact-mock-server:<version> \
  --tag ghcr.io/pact-foundation/pact-mock-server:latest \
  --push
```
